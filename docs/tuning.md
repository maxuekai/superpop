# 调参手册（手感数值与实测数据）

AGENTS.md 只写"不能改的规则"，这份文件写"为什么调成现在这样、以及实测出来的数字"。
**改任何手感数值前先读这里，改完用 `npm test` + 对应仿真脚本复核，并把新数据更新回本文件。**

## 总则

1. 先测量再调参：先算出当前值/跑仿真拿到基线，再动 `src/config.js`。
2. 一次只改一组相关参数（比如提速必须同时看 AI 能不能跟上）。
3. 改完 `npm test` 必须全绿；改了玩法逻辑还要跑对应仿真对比数值。
4. 冲突指标看哪个已经不合格：某个指标已破线时，收益指标的小幅提升不值得换。

## 速度

公式（`Ball.update`）：

```
speed(r) = 摇杆满舵 / (speedDivisor + max(0, r - 初始半径) × slowdownPerRadius) × speedUnit
```

当前：`speedDivisor=50`、`slowdownPerRadius=0.9`、`speedUnit=60` → 初始满速 **84 单位/秒**。

`npm run sim:food` 的「速度剖面」（当前值）：

| 半径 | 速度(单位/秒) | 相对初始 | 跨屏(900单位) | 跨全图(1024单位) |
|---|---|---|---|---|
| 10 | 84.0 | 100% | 10.7s | 12.2s |
| 30 | 61.8 | 74% | 14.6s | 16.6s |
| 50 | 48.8 | 58% | 18.4s | 21.0s |
| 80 | 37.2 | 44% | 24.2s | 27.6s |

- 手感标准：跨屏 **5~7 秒**比较跟手，**>12 秒**会明显觉得慢。
- 历史：原来是 `60 / 1.2` → 跨屏 12.9s / r=50 时 23.1s，用户反馈"慢"。
- 想临时试别的值：`npm run sim:food -- --divisor 44 --slowdown 0.8`（不改代码）。
- **提速的连带项**：`AI.escapeProbe` 是按速度标定的。速度提上去不补偿，AI 看不见远处墙角，
  实测被逼墙比例 **1.0% → 11.0%**；补偿到 180 后回到 0.2%。改速度必须同时看这个数。

## 食物

当前：`count=360`、`radius=3`、`clusterSize=5`、`clusterRadius=46`、`avoidGap=40`。

密度指标（`npm run sim:food` 静态指标部分）：

```
λ = count / (worldW × worldH) = 4.58e-4（颗/单位²）
平均间距 = 1/√λ = 46.7        到最近食物的期望距离 = 0.5/√λ = 23.4
进食走廊 = 2 × (球半径 + 食物半径) = 26   →  直线行进每秒期望吃到 0.83 颗
```

- **成簇而不是散点**：单颗食物在手机上只有 4~7 css px 直径，散点等于"擦身而过"；
  成簇后能看见一片、一把扫过去。
- 历史：`200 / 半径 2` → 最近食物 31.4 单位、走廊 24、手机屏内 69 颗 —— 用户反馈"吃不到东西"。
- 目标手感：最近食物 **< 25 单位**，手机屏内 **> 100 颗**，食物直径 **≥ 6 css px**。

## 互吃口径

当前：`EAT.ratio=1.15`、`EAT.absorb=0.85`，吃人条件 = **尺寸比 > ratio 且两圆重叠（中心距 ≤ r1+r2）**。

| 口径 | 阈值 | 擦边测试（大球 r=22 静止，小球全速横穿） |
|---|---|---|
| 圆心进入体内（旧） | 中心距 ≤ r1 = 22 | 31.9 / 30 / 26 全部**活着**擦过去 ❌ |
| 两圆重叠（现） | 中心距 ≤ r1+r2 = 32 | 31.9 / 30 / 26 全部**被吃** ✅ |

- 旧口径下小球可以贴着大球边缘穿过去而不死。真机反馈原话："不是应该一碰到边缘就被吃掉吗"。
  这是本类型游戏的标准口径，也是玩家对"被吃"这件事的直觉。
- **互吃阈值必须与软碰撞阈值一致（都是 r1+r2），且互吃排在软碰撞之前**。
  两者不一致时，猎物会被弹开永久锁死在半径和上、永远进不了吃者体内——谁都吃不掉谁。
  详见 `AGENTS.md`「关键行为」，那里记了踩过的两次。

**改这一项后 AI 难度的实测变化**（`npm run sim`）：

```
                平均存活   被吃轮次   被逼墙
圆心进体内（旧）   17.4s     17/20     3.6%
两圆重叠（现）     17.5s     18/20    14.5%
```

存活与被吃轮次基本不变，**贴墙率看着翻倍，其实是个离群值**：14.5% 里约 49 秒全部来自
那 2 个存活满 60 秒的局（AI 靠贴墙苟活，受威胁时自然总在墙角）。相邻的 `fleeRange`
实测：`140 → 0.1%`、`160 → 14.5%`、`200 → 1.1%`、`260 → 1.2%`。不是单调趋势，
不要因为这一个数就去动 `fleeRange`——先在真机上确认 AI 是不是真的变傻了。

## 地图尺寸与单局终点

当前：`WORLD 1280×960`、`FOOD.count 560`、`KING.mass 30000`。

**为什么曾经 68 秒就没意思了**（真机反馈"食物长在我身上"+"一直在变大"）：
`WORLD` 原来是 1024×768，实测（固定种子、玩家只追最近食物、手机竖屏 390×844）：

```
  0s   132kg  球直径  23  占视口宽   3%
 30s  3844kg  球直径 124  占视口宽  35%
 60s 23870kg  球直径 309  占视口宽  87%
 68s 31684kg  球直径 356  占视口宽 100%   ← 整屏被自己的球占满
```

- **"食物长在我身上"不是 `spawnFood` 的 bug**。实测到 r=260 仍有 100% 找到干净位置、
  落在球身上只有 0.1%。真正原因是视口里只剩球边缘那一圈食物了——每吃掉一颗，新食物都
  生成在离所有球最远的角落（`spawnFood` 按设计避开所有球），在视口外。
  **遇到"食物围着我长"先量视口内剩余数，不要先去改 spawnFood。**
- **手机上视野原本根本不缩放**：`updateViewScale` 里 `Math.max(fitScale, …)`，
  `fitScale` 是"整张地图塞进屏幕"的比例，当了地板。1024×768 时 r≈6.5 就被钳死，
  `zoomExponent` 形同虚设。世界放大后地板自然松开，缩放才真正有区间。

**尺寸是扫出来的，不是拍脑袋定的**（`npm run sim -- --worldW X --worldH Y`）：

| 世界 | 平均存活 | 被吃轮次 | 被逼墙 |
|---|---|---|---|
| 1024×768（原） | 17.5s | 18/20 | 14.5% |
| **1280×960（现）** | **20.6s** | **20/20** | **0.2%** |
| 1536×1152 | 40.9s | 14/20 | 0.5% |
| 1792×1344 | 42.5s | 9/20 | 0.0% |
| 2048×1536 | 55.6s | 2/20 | 0.0% |

地图越大 AI 越抓不到（逃跑空间和 `escapeProbe` 覆盖的世界比例都变了），2048 会让游戏
退化成纯刷食物。**想要更长的单局应该调 `KING.mass`，不要继续放大地图。**
顺带一提，原表里 1024×768 的"14.5% 被逼墙"是离群值（几乎全来自 2 个靠贴墙苟活满
60 秒的局），放大到 1280×960 后自然变成 0.2%。

**`FOOD.count` 必须跟面积同步**（560 = 360 × 1280×960 / 1024×768）来保持面密度
`λ ≈ 4.56e-4` 不变。屏内食物数 = λ × 视口面积，λ 不变观感才不变：竖屏 171 颗、
桌面 208 颗。不跟着放大的话 λ 掉一截，屏内食物不够吃。

**`KING.mass` 来自同一条成长曲线**（1280×960、完美追食）：

```
  0s 121kg → 20s 2352kg → 40s 5929kg → 60s 16384kg → 80s 32041kg → 130s 球占满屏幕
```

完美操作约 80 秒到 30000kg；实际玩家要跟 AI 抢、被杀重生，2~4 分钟。
`isCrowned` 要求**质量达标且当前第一**，只看质量会被小号互喂刷上去。

### AI 相对变弱（已修一半，比值 0.766 → 0.849）

`npm run sim:food` 的 **AI / 玩家食物获取比从 0.94 掉到 0.766**（地图放大后）。
调 `AI.foodGain` 修不回来——0.34 时比值 0.78、0.38 时反而掉到 0.67，
说明瓶颈不在收益而在**速度**。

真正的坑在 `ai.js`：`power = JOYSTICK.radius * speedScale * (fleeing ? 1 : 0.95)`，
那个 **×0.95 原本没有任何注释**，叠在 `speedScale`(0.92) 上是 0.874 倍满舵——
AI 觅食时比玩家慢 12.6%，而 `sim:food` 里 AI 孤身觅食、全程吃这个亏。

**不能靠调 `speedScale` 补**，因为它会同时加快逃跑：

| speedScale | AI/玩家食物比 | 被吃轮次 | 平均存活 | 被逼墙 |
|---|---|---|---|---|
| 0.92（原） | 0.766 | 20/20 | 20.6s | 0.2% |
| 1.00 | 0.874 | 11/20 | 32.1s | 10.8% |
| 1.05 | 0.923 | 4/20 | 32.1s | 4.4% |

"AI 吃得多"和"抓得住 AI"是**对立的**。所以只动了不影响逃跑的那个系数：

```
AI.foragePower:  0.95 → 1.0    去掉没注释的额外减速（逃跑路径不受影响）
AI.thinkInterval: 0.2 → 0.1    对追击难度零影响（实测 18/20 完全不变）
```

结果 0.766 → 0.849，追击仍是 17~18/20。

**试过但回退的**：给食物目标加滞后（"已在追的食物没远出 N 倍就不换"），
比值**纹丝不动**（0.860 全档一样）——"AI 在两个差不多远的食物之间抖"这个假设
被数据否掉了。没测出收益的复杂度不留。

**还没到 0.94，差的那部分就是 8% 速度差**（0.849 × 1.08 ≈ 0.92）。
要补齐只能动 `speedScale`，代价是追击崩。想清楚哪个更重要再动。

**仿真的坑**：`sim:food` 原本只跑 1 局 30 秒——混沌系统的单次采样没法比参数
（`foragePower` 0.95→1 单局显示 0.77→0.67，是噪声不是趋势）。
现在支持 `--trials N` 取平均，**改 AI 参数一律用 `--trials 8` 以上**。

### 视野缩放在手机上几乎不生效（已修）

`updateViewScale` 里 `Math.max(fitScale, …)` 的 `fitScale` 是"整张地图塞进屏幕"的比例，
原本作为**下限**——视口不许大于世界，否则相机会被钳到负坐标。代价是手机上
（竖屏、长边是高度）这个下限很快就起作用：

```
修复前，竖屏 390×844、世界 1280×960：fitScale = 0.8792
  半径 10 → 视口 416×900
  半径 12 → 视口 443×957      ← 缩放到这里就到顶了
  半径 80 → 视口 444×960      ← 和半径 12 几乎一样
```

修法三件事一起上：

1. **`WORLD` 1280×960 → 1280×1280**。竖屏的视野上限由世界**高度**决定，越高缩放区间越长。
2. **`VIEW.maxZoomOut = 1.3`**，允许视口达到世界的 1.3 倍。
3. **`Camera.clampView` 在视口大于世界时改为居中**。旧实现用"左边超出→贴左"和
   "右边超出→贴右"两条规则，视口大于世界时这两条互相打架：`xView` 在负坐标和 0
   之间横跳，球也偏在屏幕一侧。

实测（`node scripts/zoom-report.mjs`，手机竖屏）：

```
半径 10  (100kg)     视口 416×900   球占视口宽  5%
半径 40  (1600kg)    视口 676×1462  球占视口宽 12%
半径 58              缩放到此失效（视口 = 世界的 1.3 倍）
半径 173 (称王门槛)  视口 769×1664  球占视口宽 45%
```

- `maxZoomOut` 不能太大：视口超过世界就会露出世界外区域，1.3 是一边各露 15%；
  再大就是大片空白。
- 缩放在 r≈58 之后固定是**有意的**——保证称王门槛处球只占视口宽 45%，
  不会出现"球比屏幕还大、地图看不见了"。
- **改 `WORLD` / `VIEW.longEdgeWorld` / `zoomExponent` / `maxZoomOut` 之后要同时跑**：
  `npm run sim:food`（屏内食物数不能掉）、`npm run sim -- --worldW --worldH`（追击难度）、
  `node scripts/zoom-report.mjs --scan`（缩放区间）。三者会互相拉扯。

### 视野缩放的平滑

当前：`VIEW.zoomLerp = 6`（1/秒），60fps 下**一帧最多追上差距的 9.5%**，约 500ms 收敛到 95%。

`Game.updateViewScale` 早期是直接赋值的，而目标缩放的来源**全是硬跳变**：

| 触发 | 视口宽度的单帧跳变 | 平滑后 |
|---|---|---|
| 手机地址栏收起 844→920 | 8.3% | **0.85%** |
| 手机地址栏展开 844→700 | 20.6% | **1.65%** |
| 转屏 竖→横 | 33.3% | **2.44%** |
| 吃人（质量吸收） | ~7% | 0.7% |
| 分身合并（largestCell → √2 r） | ~11% | 1.1% |

- **必须用指数平滑，不能用线性插值**（`current + (target-current) * t`）：t 固定时跳变越大单帧越猛。
  `smoothTowards` 的单帧变化幅度只跟"还差多少"成比例，与跳变本身多大无关，所以 300% 的跳变也压得住。
- **`resize()` 不能无条件 snap**——手机地址栏收放会高频触发它，一 snap 就又回到硬跳。
  只有首次布局、以及 `begin`/`respawnPlayer`/`quitToMenu`（重开一局该立刻就位）才 snap。
- 调 `zoomLerp` 的判据：太小会拖（跟不上目标，镜头和球看着不同步），太大又回到生硬。
  6 是实测平衡点；想更跟手可以到 9（单帧 13.9%，333ms 到 95%）。

## 分裂

当前：`minCellRadius=16`（256kg 门槛）、`separation=1.4`、`pushSpeed=120`、`pushTime=0.3`、
`cooldown=8`、`mergeCooldown=3`、`mergeFactor=0.9`、`maxCells=8`。

r=16 切开的实测数字：

```
切完各半径        11.3      （√(16²/2) = 0.707 × 原半径）
初始中心距        31.7      （= 2 × separation × 切完半径）
两半径和          22.6      → 中心距 > 半径和，不重叠 ✅
合并阈值          20.4      （(r1+r2) × mergeFactor）→ 中心距 > 阈值，不会自动粘回 ✅
外冲后中心距      84.0      （外冲约 +52，跑完 0.3s 后停住不再变）
屏幕长边占比      3.5% → 9.3%
```

- **间距必须按「切完之后的半径」算，不能按原半径**。按原半径 × 0.35 算出来是
  中心距 11.2 < 半径和 22.6 —— 两半直接叠在一起；又因为 11.2 < 合并阈值 20.4，
  `mergeCooldown`（3s）一到就被吸回一个球。真机反馈原话是"分裂也没有分裂多远，
  还是很近"+"按了没反应"，两个症状是同一个根因。
- **外冲是纯手感，不是规则**：两半朝同一方向以同一速度走，距离会永远停在初始间距上，
  看起来就像球"变胖"而不是"裂开"。单侧总位移 ≈ `pushSpeed × pushTime / 2`，
  按 `√(切完半径 / 初始半径)` 缩放——纯线性会让大球的分裂在屏幕上占掉近两成，
  平方根则接近"屏幕上每次看起来差不多"（相机视野本身按 `(r/初始r)^0.35` 缩放）。
- **验收口径**：切完立刻量中心距，必须同时 `> 两半径和` 且 `> (r1+r2) × mergeFactor`；
  再跑 5 秒确认距离停住而不是一路拉开。这两条都在 `npm test` 里。

## 玩家 vs AI 的成长平衡

`PLAYER.growthPerFood=0.5`（玩家），`AI.foodGain=0.3`（AI）。
食物一多，AI 吃得也快，用 `foodGain` 把它们的成长按回来。实测 30 秒觅食：

| | 旧（200 颗食物） | 现（360 颗食物） |
|---|---|---|
| 玩家 | 100 → 2304kg | 100 → 3025kg |
| AI | 100 → 1040kg | 100 → 1260kg |

验收口径：**玩家长得更快、AI 难度没变**。如果 AI 涨得比玩家快，调低 `AI.foodGain`。

## AI 行为参数

决策优先级：逃离更大的球 > 追击更小的球 > 最近的食物 > 随机游走。决策每 `thinkInterval`(0.2s) 重选，转向每步算。

**`fleeRange`（当前 160）** —— 手感关键，两头都会坏：

| fleeRange | 平均存活 | 被吃轮次 | 被逼墙 |
|---|---|---|---|
| 120 | 29.4s | 12/20 | 高 |
| **160（现）** | **17.4s** | **17/20** | **3.6%** |
| 320 | 8.9s | 16/20 | 0% |

太大 → AI 一看见玩家就全程逃、永远抓不到；太小 → AI 懒得躲。

> 旧表里 160 行的"0.2%"是**错的**：那时的 `flee-sim.js` 没有调用 `resolveOverlaps`，
> 等于在一个没有软碰撞的世界里测的。补上之后猎手才真正贴得上猎物，贴墙率变成 3.6%。
> **仿真必须与 `Game.updateWorld` 同序（吃 → 弹开），漏掉任何一步都会得出假结论。**

**`escapeDirection` 的打分项**（`escapeSamples=16` 个均分方向，各探测 `escapeProbe` 距离）：

```
得分 = 离威胁更远(加) − 贴墙(减，越近减越狠) − 撞向别的球(减) − 靠近顺手食物(减)
```

没有这套打分时 AI 沿"远离威胁"直线跑，会被一路逼到墙角撞死（实测存活 2.9s → 11.5s）。
`escapePhase` 是每个 AI 独立的随机相位，重新决策时按 `escapeChange`(0.25) 换一侧，于是不同 AI 走位不同。

**`escapeFoodWeight`（当前 0.1）** —— 逃跑时顺手吃路边食物的吸引力：

| 权重 | 每轮多吃 | 被逼墙 |
|---|---|---|
| 0.25 | +1 颗 | **8.7%（破线）** |
| **0.1（现）** | 基准 | **1.3%** |

**AI 出生半径**：`[0.8, 2.2] × 初始半径`，上限 = 玩家当前半径 × `spawnRadiusRatio`(1.05)。
开局只放 `targetAiCount()` 个（= `minCount`），不按 `count` 放满，否则开局容易被围。
**AI 出生/重生优先挑相机视口之外的位置**（`rules.isOutsideView`），否则会在玩家眼前凭空出现、像"闪现"。

**AI 互相避让（`avoidGap` / `avoidWeight`）**：小球靠近到「双方半径 + 55」以内会按接近程度互相推开，
所有模式都生效（觅食/追击/游走/逃跑）。之前只有逃跑的 `escapeDirection` 算了"别撞球"，
觅食和追击完全不避让，再叠加"所有 AI 都选最近的同一颗食物"，于是它们走成一条直线。
**逃跑时要跳过当前威胁**——`escapeDirection` 已经算过一次，重复叠加会让猎物过分灵活
（实测玩家平均存活 17.4s → 30.0s、贴墙 0.2% → 5.9%），跳过之后回到 17.4s / 0.2%。

避让效果（90 秒拥挤度仿真，邻居 = 身边 80 单位内的 AI）：

| AI 数量 | 两两平均距离（改前→改后） | 平均邻居数（改前→改后） |
|---|---|---|
| 6 | 346 → 271 | 0.24 → 0.34 |
| 8 | 270 → **336** | 0.91 → **0.26** |
| 12 | 298 → **343** | 0.96 → **0.43** |

（6 AI 那档反而略挤，是因为地图大、球只有 6 个，差异在噪声范围内。）

**目标认领**：`think()` 会跳过其他 AI 已经盯上的猎物/食物（看它们的 `targetBall`/`targetFood`/`escapeFood`），
否则一群 AI 会同时奔向同一个点。

## AI 之间会不会互吃

会，但**稀疏**。无头仿真（90 秒、只有 AI、无食物补给差异）实测：

| AI.eatBonus | 6 AI | 8 AI | 12 AI |
|---|---|---|---|
| 1（原始） | 6 次，体型 20.6~48.5 | 11 次，16.2~38.1 | 22 次，9.8~42.2 |
| **1.3（当前）** | 10 次，11.5~60.3 | 10 次，9.7~59.5 | 22 次，8.2~68.4 |
| 1.6 | 15 次，8.6~111.8（滚雪球） | 13 次，9.3~63.6 | 18 次，10.4~58.0 |

为什么玩家几乎看不到：一次互吃只给 `0.85 × 对方质量`（r=10 的猎物 ≈ 85 质量，对 400 质量的捕食者是 +21% 质量、**半径只涨 4%**），
而且大多发生在屏幕外。`eatBonus` 就是为了把这个"看不见的成长"放大到能被察觉，1.6 会滚雪球出霸主，故取 1.3。
注意倍率越高 AI 整体越肥（12 AI 合计质量 6350 → 9766），游戏会变难——再往上加之前先重测难度。

复现：改 `AI.eatBonus` 后跑 AI 互吃仿真（见下方脚本骨架，同样要固定种子）；只看 `npm run sim` 不够，
那个脚本里的猎物只吃食物、不吃别的球，测不到 eatBonus。

## 「大球追不上」的验收口径

**别看速度公式下结论**：

- 真正的小体型硬门槛是**互吃比例**（`r > 对方r × 1.15`）。猎手 r=10 对 r=10 是 **0/20** 轮吃到，r=12 就 **20/20**——差一点点永远吃不到，跟速度无关。
- 速度只是一阶估算。实测猎手比猎物慢 40%（r=50 vs r=10）仍抓到 **16/20**，因为逃命 AI 达不到理论速度、有界地图躲不了角落、还会边逃边长大。

```bash
npm run sim -- --sweep              # 扫猎手半径 10~50，出"理论直退 vs 实测被吃"对照
npm run sim -- --hunter 30 --prey 15
npm run sim -- --nofood             # 关掉"猎物边逃边长大"，把速度因素单独隔离出来
```

## 仿真脚本用法

两个脚本都：**固定随机种子**（结果可复现）、**支持参数覆盖**、**只输出少量关键指标 + 异常提示**。

```bash
npm run sim                                   # AI 逃跑：fleeRange/escapeProbe/escapeWallWeight/escapeFoodWeight/escapeFoodRange
npm run sim -- 160 180                       # 位置参数按上面顺序覆盖
npm run sim -- --sweep --hunter 30 --prey 15 --nofood
npm run sim:food                              # 食物密度/速度剖面/成长对比
npm run sim:food -- --divisor 44 --slowdown 0.8 --playerGain 0.6 --foodGain 0.25
```

**写仿真脚本时的坑**（都踩过）：

- 密度公式用**面密度 `λ`**（单位²），不是平均间距（单位长度）——用错会让所有结论偏一个数量级。
- 参数解析要区分 flag 的值和位置参数：`--divisor 60` 里的 `60` 若又被当位置参数，会顺手改掉别的配置，
  导致整组对照数据作废（当时就是这么废掉一轮的）。**验证方式：不带参数跑一遍，结果应与不带覆盖的 `npm run sim` 一致。**
- 解析模型和仿真矛盾时，先怀疑仿真里的硬编码假设（例如猎手半径写死 22，正好没覆盖失败的体型区间），
  并把结论降级为"倾向 + 需补测"，不要拿手算冒充仿真结果。
