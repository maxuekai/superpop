# 调参手册（手感数值与实测数据）

AGENTS.md 只写"不能改的规则"，这份文件写"为什么调成现在这样、以及实测出来的数字"。
**改任何手感数值前先读这里，改完用 `npm test` + 对应仿真脚本复核，并把新数据更新回本文件。**

## 总则

1. 先测量再调参：先算出当前值/跑仿真拿到基线，再动 `src/config.js`。
2. 一次只改一组相关参数（比如提速必须同时看 AI 能不能跟上）。
3. 改完 `npm test` 必须全绿；改了玩法逻辑还要跑对应仿真对比数值。
4. 冲突指标看哪个已经不合格：某个指标已破线时，收益指标的小幅提升不值得换。

## 速度

公式（`Ball.update`）：

```
speed(r) = 摇杆满舵 / (speedDivisor + max(0, r - 初始半径) × slowdownPerRadius) × speedUnit
```

当前：`speedDivisor=44`、`slowdownPerRadius=0.8`、`speedUnit=60` → 初始满速 **95.5 单位/秒**。

`npm run sim:food` 的「速度剖面」（当前值）：

| 半径 | 速度(单位/秒) | 相对初始 | 跨屏(900单位) | 跨全图(1280单位) |
|---|---|---|---|---|
| 10 | 95.5 | 100% | 9.4s | 13.4s |
| 30 | 70.0 | 73% | 12.9s | 18.3s |
| 50 | 55.3 | 58% | 16.3s | 23.2s |
| 80 | 42.0 | 44% | 21.4s | 30.5s |

- 手感标准：跨屏 **5~7 秒**比较跟手，**>12 秒**会明显觉得慢。
- 历史：`60 / 1.2` → 跨屏 12.9s（用户反馈"慢"）；`50 / 0.9` → 10.7s；`44 / 0.8` → 9.4s。
- 想临时试别的值：`npm run sim:food -- --divisor 44 --slowdown 0.8`（不改代码）。

### 提速必须同比例缩 slowdown（50/0.9 → 44/0.8 的实测）

`slowdownPerRadius` 是**加性**项：只缩 `speedDivisor` 会让大球多背的减速占比相对变大，
小球相对更快 → 玩家追不到 AI。猎手 r=22 / 猎物 r=10 的速度比（猎物÷猎手）：

```
50 / 0.9（旧）  = 60.8/50 = 1.216
44 / 0.9（只缩分母）= 54.8/44 = 1.245   ← 猎物优势拉大
44 / 0.8（现）  = 53.6/44 = 1.218   ← 比例保住
```

flee-sim 实测（80 轮为权威口径，40 轮的 ±6.6% 噪声会翻转结论）：

| 方案 | 被吃(40轮) | 被吃(80轮) | 平均存活 | 被逼墙 | AI/玩家食物比 |
|---|---|---|---|---|---|
| 50 / 0.9（旧） | 32/40 | 62/80 | 26.1s | 1.2% | 0.849 |
| 44 / 0.9 | 25/40 | — | 34.6s | 2.9% | — |
| 44 / 0.87 | 29/40 | — | 27.9s | 3.0% | 0.873 |
| **44 / 0.8（现）** | 29/40 | **61/80** | 29.5s | 2.0% | 0.867 |

44/0.9 的 62.5% 比当年被否掉的 1536×1152 地图（70%）还差，不能接受；
44/0.8 追猎保持（61 vs 62）、贴墙 2.0% 合格、觅食比 0.867 仍在 0.94 以内。
**改 divisor 时 slowdown 按同比例动**（0.8 = 0.9 × 44/50），r=50 的相对速度保持在 58%。

- **提速的连带项**：`AI.escapeProbe` 是按速度标定的。60→50 那次不补偿，被逼墙比例
  **1.0% → 11.0%**，补偿到 180 后回到 0.2%。这次 50→44（×1.14 速度）实测 probe=180
  仍够用（贴墙 2.0%），未再上调；再提速度时先看这个数。
- TODO 里旧的"divisor=44 会让贴墙率飙到 32%"是**旧世界尺寸下的过时数据**
  （当时还没放大到 1280×1280、probe 也还没补偿）——提速前先复测，别被历史结论挡住。

## 食物

当前：`count=747`、`radius=3`、`clusterSize=5`、`clusterRadius=46`、`avoidGap=40`、`radiusJitter=0.13`。

密度指标（`npm run sim:food` 静态指标部分）：

```
λ = count / (worldW × worldH) = 4.58e-4（颗/单位²）
平均间距 = 1/√λ = 46.7        到最近食物的期望距离 = 0.5/√λ = 23.4
进食走廊 = 2 × (球半径 + 食物半径) = 26   →  直线行进每秒期望吃到 0.83 颗
```

- **成簇而不是散点**：单颗食物在手机上只有 4~7 css px 直径，散点等于"擦身而过"；
  成簇后能看见一片、一把扫过去。
- 历史：`200 / 半径 2` → 最近食物 31.4 单位、走廊 24、手机屏内 69 颗 —— 用户反馈"吃不到东西"。
- 目标手感：最近食物 **< 25 单位**，手机屏内 **> 100 颗**，食物直径 **≥ 6 css px**。

### 食物视觉（2026-10 实施记录）

改之前的真实状态：代码里每颗食物各自挑簇心、各自随机色，`clusterSize` 是死配置——
即"均匀散点 + 全随机色"，画面糊成彩屑（AGENTS.md 写的"成簇生成"只对了一半）。
本次把簇做真，并加两项纯视觉优化：

1. **真成簇 + 簇内同色**：`seedFood()` 按 `clusterSize`(5) 颗/簇铺满 `count`；
   同簇共享簇心与颜色。被吃掉的单颗由 `spawnFood()` 重生——贴着一颗随机幸存食物落子
   并**继承它的颜色**，簇被吃掉后从邻居"长回来"而不是退化成散点。
   副作用：簇会缓慢变大（锚点随机、每局 `seedFood` 重置），一局内幅度很小。
2. **半径抖动**：`radiusJitter=0.13` → 每颗绘制半径 3×(1±0.13) ≈ 2.6~3.4 世界单位。
   一簇里大小略有参差才有"一撮吃的"质感，完全等大像贴图。
   **抖动只作用于绘制与视口裁剪，不进吃判定**——碰撞仍用基准 `radius`（差 0.4 世界单位，
   球半径 ≥10，感知不到，不值得为此动判定路径）。

实测（浏览器 ?debug=1，全新开局）：

- 近邻对（间距 ≤ 46）同色率 **0.557**，随机色基线 1/6 ≈ 0.167；泵 30 秒对局
  （AI 大量进食触发重生）后 **0.576**——重生继承颜色让片越补越匀。
- 半径实测 min/max 2.61/3.39；食物总数在被吃+补种动态下恒定 747；零 JS 报错。
- 截图观感：同色小片可辨、大小参差明显；相邻簇偶发撞色（1/6）连成更大散片，属自然效果。

**红线**（评估时定下的，别再提）：

- **具象图案**（寿司/水果形状）：手机上 5.6 css px，任何细节糊成渣；
- **逐颗渐变/描边色**：破坏按色合批（同一 fillStyle 才能一条 path 画完 747 颗）。

未做的候选：双层高光（糖珠感，桌面收益、手机不可见）、呼吸动画（每帧 747 次重绘不合批逻辑，
帧预算换不来玩法价值）。手机食物直径 5.6 < 6px 目标——要达标只能动 `FOOD.radius`，
那是玩法数值，走 `npm run verify` 全套再议。

### 空间覆盖：重生锚定的"荒漠漂移"与 emptyRegionBias（2026-10-11，真机反馈）

纯邻居锚定的重生有个结构性盲区：**被吃光的区域永远没有锚点**——食物只会在"还有食物的地方"
重生。联机一局吃的人多、时间长，漂移远比单机严重（单机回合短 + 每局 seedFood 重置掩盖了它）。
真机表现就是"刚出生吃不动东西"：出生点周围是食物荒漠。

实测（一次性脚本：8 个 AI 持续进食，8×8 网格看覆盖，种子 424242）：

| 时间 | 空格子(/64) | 单格最少/最多 | 新玩家出生点最近食物距离 |
|---|---|---|---|
| 0s | 2 | 0/36 | 30 |
| 120s | 54 | 0/354 | 246 |
| 360s | **62** | 0/489 | **1060** |

修复：`FOOD.emptyRegionBias=0.25`——每颗重生有 25% 概率改投「当前最空的格子」（8×8 粗网格，
数一遍 747 颗取最少者，开销可忽略），新种子用随机色，之后仍走邻居锚定长成簇。
修复后同场景：6 分钟时空格子 62 → **5**，出生点最近食物 1060 → **47**；
`npm run verify` 全绿，AI/玩家觅食比 0.867 与被吃率 17/20 锚点不动（空间再分布不影响总量与速率）。

代价与边界：25% 的新食物是"孤点种子"，短时间看同色率略降（成片感靠种子长回簇补偿）；
大簇仍会缓慢变胖（max 到 556）——那是邻居锚定的固有属性，覆盖保住后不影响玩法。
若日后要再调：bias 调大 = 空区回填更快但簇更碎；调小 = 簇感更强但荒漠更快。


## 互吃口径

当前：`EAT.ratio=1.15`、`EAT.absorb=0.85`，吃人条件 = **尺寸比 > ratio 且两圆重叠（中心距 ≤ r1+r2）**。

| 口径 | 阈值 | 擦边测试（大球 r=22 静止，小球全速横穿） |
|---|---|---|
| 圆心进入体内（旧） | 中心距 ≤ r1 = 22 | 31.9 / 30 / 26 全部**活着**擦过去 ❌ |
| 两圆重叠（现） | 中心距 ≤ r1+r2 = 32 | 31.9 / 30 / 26 全部**被吃** ✅ |

- 旧口径下小球可以贴着大球边缘穿过去而不死。真机反馈原话："不是应该一碰到边缘就被吃掉吗"。
  这是本类型游戏的标准口径，也是玩家对"被吃"这件事的直觉。
- **互吃阈值必须与软碰撞阈值一致（都是 r1+r2），且互吃排在软碰撞之前**。
  两者不一致时，猎物会被弹开永久锁死在半径和上、永远进不了吃者体内——谁都吃不掉谁。
  详见 `AGENTS.md`「关键行为」，那里记了踩过的两次。

**改这一项后 AI 难度的实测变化**（`npm run sim`）：

```
                平均存活   被吃轮次   被逼墙
圆心进体内（旧）   17.4s     17/20     3.6%
两圆重叠（现）     17.5s     18/20    14.5%
```

存活与被吃轮次基本不变，**贴墙率看着翻倍，其实是个离群值**：14.5% 里约 49 秒全部来自
那 2 个存活满 60 秒的局（AI 靠贴墙苟活，受威胁时自然总在墙角）。相邻的 `fleeRange`
实测：`140 → 0.1%`、`160 → 14.5%`、`200 → 1.1%`、`260 → 1.2%`。不是单调趋势，
不要因为这一个数就去动 `fleeRange`——先在真机上确认 AI 是不是真的变傻了。

## 地图尺寸与单局终点

当前：`WORLD 1280×1280`、`FOOD.count 747`、`KING.mass 45000`（2026-10-18 起，见下）。

**为什么曾经 68 秒就没意思了**（真机反馈"食物长在我身上"+"一直在变大"）：
`WORLD` 原来是 1024×768，实测（固定种子、玩家只追最近食物、手机竖屏 390×844）：

```
  0s   132kg  球直径  23  占视口宽   3%
 30s  3844kg  球直径 124  占视口宽  35%
 60s 23870kg  球直径 309  占视口宽  87%
 68s 31684kg  球直径 356  占视口宽 100%   ← 整屏被自己的球占满
```

- **"食物长在我身上"不是 `spawnFood` 的 bug**。实测到 r=260 仍有 100% 找到干净位置、
  落在球身上只有 0.1%。真正原因是视口里只剩球边缘那一圈食物了——每吃掉一颗，新食物都
  生成在离所有球最远的角落（`spawnFood` 按设计避开所有球），在视口外。
  **遇到"食物围着我长"先量视口内剩余数，不要先去改 spawnFood。**
- **手机上视野原本根本不缩放**：`updateViewScale` 里 `Math.max(fitScale, …)`，
  `fitScale` 是"整张地图塞进屏幕"的比例，当了地板。1024×768 时 r≈6.5 就被钳死，
  `zoomExponent` 形同虚设。世界放大后地板自然松开，缩放才真正有区间。

**尺寸是扫出来的，不是拍脑袋定的**（`npm run sim -- --worldW X --worldH Y`）：

| 世界 | 平均存活 | 被吃轮次 | 被逼墙 |
|---|---|---|---|
| 1024×768（原） | 17.5s | 18/20 | 14.5% |
| **1280×960（现）** | **20.6s** | **20/20** | **0.2%** |
| 1536×1152 | 40.9s | 14/20 | 0.5% |
| 1792×1344 | 42.5s | 9/20 | 0.0% |
| 2048×1536 | 55.6s | 2/20 | 0.0% |

地图越大 AI 越抓不到（逃跑空间和 `escapeProbe` 覆盖的世界比例都变了），2048 会让游戏
退化成纯刷食物。**想要更长的单局应该调 `KING.mass`，不要继续放大地图。**
顺带一提，原表里 1024×768 的"14.5% 被逼墙"是离群值（几乎全来自 2 个靠贴墙苟活满
60 秒的局），放大到 1280×960 后自然变成 0.2%。

**`FOOD.count` 必须跟面积同步**（560 = 360 × 1280×960 / 1024×768）来保持面密度
`λ ≈ 4.56e-4` 不变。屏内食物数 = λ × 视口面积，λ 不变观感才不变：竖屏 171 颗、
桌面 208 颗。不跟着放大的话 λ 掉一截，屏内食物不够吃。

**`KING.mass` 来自同一条成长曲线**（1280×960、完美追食）：

```
  0s 121kg → 20s 2352kg → 40s 5929kg → 60s 16384kg → 80s 32041kg → 130s 球占满屏幕
```

完美操作约 80 秒到 30000kg；实际玩家要跟 AI 抢、被杀重生，2~4 分钟。
`isCrowned` 要求**质量达标且当前第一**，只看质量会被小号互喂刷上去。

**30000 → 45000（2026-10-18，联机真机反馈"称王太快，别人没有体验"）**：
30000 是按单机吃食物曲线定的，联机里领先者吃 AI 滚雪球（每只吸收 85% ≈ +1700kg），
实测 2~3 分钟就终局、落后者刚起势。45000 的估算：吃食物 60s 到 ~10000kg
+ 再猎 ~15 只 AI ≈ 4~5 分钟一局。**与 `VIEW.maxZoomOut` 耦合**（1.3 → 1.6）：
称王 r=212 在 1.3 倍封顶视口下占宽 55%，撞"称王处球占视口 <50%"不变量；
1.6 时占 44.8%，保持 45% 口径——动 `KING.mass` 必须重算 `maxZoomOut`。
验收：verify 127/127 + invariants 11/11（含两条称王硬线）、zoom-report 称王处
45%、endgame-check 60s 可达门槛（360s 后"被 AI 卡住"与 30000 时代逐位相同，
系固定种子下的既有现象，非回归）；锚点食物比 0.867 不动。联机局长待真机复测。

### AI 相对变弱（已修一半，比值 0.766 → 0.849）

`npm run sim:food` 的 **AI / 玩家食物获取比从 0.94 掉到 0.766**（地图放大后）。
调 `AI.foodGain` 修不回来——0.34 时比值 0.78、0.38 时反而掉到 0.67，
说明瓶颈不在收益而在**速度**。

真正的坑在 `ai.js`：`power = JOYSTICK.radius * speedScale * (fleeing ? 1 : 0.95)`，
那个 **×0.95 原本没有任何注释**，叠在 `speedScale`(0.92) 上是 0.874 倍满舵——
AI 觅食时比玩家慢 12.6%，而 `sim:food` 里 AI 孤身觅食、全程吃这个亏。

**不能靠调 `speedScale` 补**，因为它会同时加快逃跑：

| speedScale | AI/玩家食物比 | 被吃轮次 | 平均存活 | 被逼墙 |
|---|---|---|---|---|
| 0.92（原） | 0.766 | 20/20 | 20.6s | 0.2% |
| 1.00 | 0.874 | 11/20 | 32.1s | 10.8% |
| 1.05 | 0.923 | 4/20 | 32.1s | 4.4% |

"AI 吃得多"和"抓得住 AI"是**对立的**。所以只动了不影响逃跑的那个系数：

```
AI.foragePower:  0.95 → 1.0    去掉没注释的额外减速（逃跑路径不受影响）
AI.thinkInterval: 0.2 → 0.1    对追击难度零影响（实测 18/20 完全不变）
```

结果 0.766 → 0.849，追击仍是 17~18/20。

**试过但回退的**：给食物目标加滞后（"已在追的食物没远出 N 倍就不换"），
比值**纹丝不动**（0.860 全档一样）——"AI 在两个差不多远的食物之间抖"这个假设
被数据否掉了。没测出收益的复杂度不留。

**还没到 0.94，差的那部分就是 8% 速度差**（0.849 × 1.08 ≈ 0.92）。
要补齐只能动 `speedScale`，代价是追击崩。想清楚哪个更重要再动。

**仿真的坑**：`sim:food` 原本只跑 1 局 30 秒——混沌系统的单次采样没法比参数
（`foragePower` 0.95→1 单局显示 0.77→0.67，是噪声不是趋势）。
现在支持 `--trials N` 取平均，**改 AI 参数一律用 `--trials 8` 以上**。

### 视野缩放在手机上几乎不生效（已修）

`updateViewScale` 里 `Math.max(fitScale, …)` 的 `fitScale` 是"整张地图塞进屏幕"的比例，
原本作为**下限**——视口不许大于世界，否则相机会被钳到负坐标。代价是手机上
（竖屏、长边是高度）这个下限很快就起作用：

```
修复前，竖屏 390×844、世界 1280×960：fitScale = 0.8792
  半径 10 → 视口 416×900
  半径 12 → 视口 443×957      ← 缩放到这里就到顶了
  半径 80 → 视口 444×960      ← 和半径 12 几乎一样
```

修法三件事一起上：

1. **`WORLD` 1280×960 → 1280×1280**。竖屏的视野上限由世界**高度**决定，越高缩放区间越长。
2. **`VIEW.maxZoomOut = 1.3`**，允许视口达到世界的 1.3 倍（现值 1.6，随 KING.mass
   45000 配套调整，见"地图尺寸与单局终点"）。
3. **`Camera.clampView` 在视口大于世界时改为居中**。旧实现用"左边超出→贴左"和
   "右边超出→贴右"两条规则，视口大于世界时这两条互相打架：`xView` 在负坐标和 0
   之间横跳，球也偏在屏幕一侧。

实测（`node scripts/zoom-report.mjs`，手机竖屏）：

```
半径 10  (100kg)     视口 416×900   球占视口宽  5%
半径 40  (1600kg)    视口 676×1462  球占视口宽 12%
半径 105             缩放到此失效（视口 = 世界的 1.6 倍；1.3 时代是 r≈58）
半径 212 (称王门槛)  视口 946×2048  球占视口宽 45%
```

- `maxZoomOut` 不能太大：视口超过世界就会露出世界外区域，1.6 是竖屏上下各露
  ~30%（底下是 body 的 #071e1c 暗底，与地图渐变同族）；1.3 → 1.6 是 KING.mass
  45000 的配套（见上），单独动它得掂量露出的空白。
- 缩放在 r≈105 之后固定是**有意的**——保证称王门槛处球只占视口宽 45%，
  不会出现"球比屏幕还大、地图看不见了"。
- **改 `WORLD` / `VIEW.longEdgeWorld` / `zoomExponent` / `maxZoomOut` 之后要同时跑**：
  `npm run sim:food`（屏内食物数不能掉）、`npm run sim -- --worldW --worldH`（追击难度）、
  `node scripts/zoom-report.mjs --scan`（缩放区间）。三者会互相拉扯。

### 视野缩放的平滑

当前：`VIEW.zoomLerp = 6`（1/秒），60fps 下**一帧最多追上差距的 9.5%**，约 500ms 收敛到 95%。

`Game.updateViewScale` 早期是直接赋值的，而目标缩放的来源**全是硬跳变**：

| 触发 | 视口宽度的单帧跳变 | 平滑后 |
|---|---|---|
| 手机地址栏收起 844→920 | 8.3% | **0.85%** |
| 手机地址栏展开 844→700 | 20.6% | **1.65%** |
| 转屏 竖→横 | 33.3% | **2.44%** |
| 吃人（质量吸收） | ~7% | 0.7% |
| 分身合并（largestCell → √2 r） | ~11% | 1.1% |

- **必须用指数平滑，不能用线性插值**（`current + (target-current) * t`）：t 固定时跳变越大单帧越猛。
  `smoothTowards` 的单帧变化幅度只跟"还差多少"成比例，与跳变本身多大无关，所以 300% 的跳变也压得住。
- **`resize()` 不能无条件 snap**——手机地址栏收放会高频触发它，一 snap 就又回到硬跳。
  只有首次布局、以及 `begin`/`respawnPlayer`/`quitToMenu`（重开一局该立刻就位）才 snap。

### 手动缩放（滚轮 / +、− / 双指捏合）

当前：`VIEW.userZoomMin=0.5`、`userZoomMax=2.0`、`KEYS.zoomStep=1.12`（2026-10 新增）。

- **`game.userZoom` 是乘在自动缩放上的系数**，不是绝对缩放——玩家长大后自动缩放照常
  缩小视野，手动值作为偏好叠在上面。合成公式在 `utils.zoomTarget`：
  `clamp(auto × userZoom, fitScale, auto × userZoomMax)`。
- **缩出钳在 `fitScale`**：fitScale 已含 `maxZoomOut=1.6` 的包络，往下放会露出更多
  世界外空白、也架空「称王处球占视口 45%」这类口径。拉到底时（桌面 1280×720 css）
  视口 2048×1152（= 世界的 1.6 倍，居中），包络不破。
- **缩进钳在自动值 × 2**：不设上限的话能把视野缩到一颗食物占满屏，没有玩法价值。
- 输入三路都汇到 `Game.zoomBy(factor)`：滚轮一格 `wheelZoomFactor` ≈ ×0.88
  （像素/行/页三种 deltaMode 已归一）、键盘一次 ×1.12（按住靠系统自动重复）、
  捏合 = 两指距离比（增量式，中途回拉视野跟着回）。Ctrl+滚轮留给浏览器页面缩放。
- **捏合与摇杆共存**（`joystick.js`）：第二根**画布**手指进捏合（摇杆暂停、面板藏、方向清零
  ——两指一起动时第一根的位移是噪声），捏合结束摇杆原地恢复（重新锚定，不跳方向）；
  **界面上的手指永远不进捏合**，否则移动中点不到分裂。
- `userZoom` 不随重开一局清零——它是视角偏好，不是游戏状态。
- 实测（?debug=1 + 合成事件）：滚轮 3 格 userZoom 1→1.455（理论 1.456）、
  键盘档位精确 ×1.12、捏合把 userZoom 顶到 2.0 上限、scale 平滑收敛无跳变、零 JS 报错。
- 测试注意：别用「替换 window.requestAnimationFrame 手动泵帧」的老办法测这个页面后
  再截图——补丁的回调存在内核闭包里，内核销毁后页面的帧循环就永久断了（canvas 不再
  出新帧，DOM 靠 interval 还在动，极具迷惑性）。要截图就保持真实 RAF（面板前台）。
- 调 `zoomLerp` 的判据：太小会拖（跟不上目标，镜头和球看着不同步），太大又回到生硬。
  6 是实测平衡点；想更跟手可以到 9（单帧 13.9%，333ms 到 95%）。

## 分裂

当前：`minCellRadius=16`（256kg 门槛）、`separation=1.4`、`pushSpeed=120`、`pushTime=0.3`、
`cooldown=8`、`mergeCooldown=3`、`mergeFactor=0.9`、`maxCells=8`。

r=16 切开的实测数字：

```
切完各半径        11.3      （√(16²/2) = 0.707 × 原半径）
初始中心距        31.7      （= 2 × separation × 切完半径）
两半径和          22.6      → 中心距 > 半径和，不重叠 ✅
合并阈值          20.4      （(r1+r2) × mergeFactor）→ 中心距 > 阈值，不会自动粘回 ✅
外冲后中心距      84.0      （外冲约 +52，跑完 0.3s 后停住不再变）
屏幕长边占比      3.5% → 9.3%
```

- **间距必须按「切完之后的半径」算，不能按原半径**。按原半径 × 0.35 算出来是
  中心距 11.2 < 半径和 22.6 —— 两半直接叠在一起；又因为 11.2 < 合并阈值 20.4，
  `mergeCooldown`（3s）一到就被吸回一个球。真机反馈原话是"分裂也没有分裂多远，
  还是很近"+"按了没反应"，两个症状是同一个根因。
- **外冲是纯手感，不是规则**：两半朝同一方向以同一速度走，距离会永远停在初始间距上，
  看起来就像球"变胖"而不是"裂开"。单侧总位移 ≈ `pushSpeed × pushTime / 2`，
  按 `√(切完半径 / 初始半径)` 缩放——纯线性会让大球的分裂在屏幕上占掉近两成，
  平方根则接近"屏幕上每次看起来差不多"（相机视野本身按 `(r/初始r)^0.35` 缩放）。
- **验收口径**：切完立刻量中心距，必须同时 `> 两半径和` 且 `> (r1+r2) × mergeFactor`；
  再跑 5 秒确认距离停住而不是一路拉开。这两条都在 `npm test` 里。

### 合并的顿挫（`SPLIT.mergeStun*`，2026-10-17）

分裂有外冲、有冷却文案，合并却什么都不发生——玩家会觉得"两半自己糊回去了，不像合并"。
补一记顿挫：`mergeStunSeconds=0.28`、`mergeStunSlow=0.5`（僵直刚发生时的位移比例，
取 0.5 而不是 0：真僵住会像卡住）、`mergeStunWobble=0.12`（视觉挤压）、`mergeStunHz=9`。

- 折扣与挤压幅度都由**剩余僵直时间**线性驱动，所以恢复也是渐进的；
  一帧直接恢复会像"卡了一下又猛地弹出去"。
- 纯表现：质量守恒、合并阈值、判定都不动。
- **最后一帧必须把 `mergeWobble` 清零**。留个 k 的残值（0.0057 这种看着无害）就是
  "球从此永远是椭的"——单测第一次跑就抓到了这个。
- 僵直作用于**输入驱动的位移**，不作用于分裂外冲（外冲是一次性的动画）。

## 玩家 vs AI 的成长平衡

`PLAYER.growthPerFood=0.5`（玩家），`AI.foodGain=0.3`（AI）。
食物一多，AI 吃得也快，用 `foodGain` 把它们的成长按回来。实测 30 秒觅食：

| | 旧（200 颗食物） | 现（360 颗食物） |
|---|---|---|
| 玩家 | 100 → 2304kg | 100 → 3025kg |
| AI | 100 → 1040kg | 100 → 1260kg |

验收口径：**玩家长得更快、AI 难度没变**。如果 AI 涨得比玩家快，调低 `AI.foodGain`。

## 死亡演出

当前：`DEATH.cueSeconds=0.8`、`DEATH.slowMoScale=0.25`，红闪 = `.death-flash` 径向渐变
（中心透明 → 边缘 `rgba(255,45,45,0.55)`），CSS 动画 1.5s 自行淡出（比演出长，弹结算时还在收尾）。

- **演出计时用真实秒**（`dyingTimer` 按 dt 递减），**慢放只作用于世界推进**（`this.time` 跟世界走，
  否则 AI 重生倒计时会相对世界提前）；相机/HUD 仍按实时更新，结算数据在死亡瞬间定格。
- 浏览器实测（?debug=1 + 手动逐帧泵）：dying 恰好 48 帧（0.8s）、慢放精确 0.25×
  （每 0.1s 实时只推进 0.025s 游戏时间）、红闪 class 全程在位、结束后立即弹结算、零 JS 报错。
- 0.8s/0.25× 是拍的初值：>1.2s 玩家会急着点屏幕，<0.5s 等于没有。
- **真机观感待验**：视觉模型评价红闪峰值（alpha 0.55）"偏含蓄"；实测中被结算层暗色
  （rgba(3,20,18,0.72)，z-10）压着看更弱，但真实时序里红闪峰值出现在结算弹出**之前**，
  直接叠在游戏画面上会更明显。真机觉得不够醒目 → 调 `index.css` 渐变里的 0.55。
- 测试钩子：`?debug=1` 暴露 `window.__game`（后台标签页 RAF 被浏览器节流、世界冻结，
  无头测试需要它来读状态/驱动死亡）。

## 渲染层：维持 canvas 2D（2026-10-17 评估，结论：不换）

有人问过"能不能把渲染引擎换成成熟框架（PixiJS / Phaser 之类）"。
结论是**技术上能换、迁移面很小，但现在没有理由换；而通用游戏引擎恰恰是最不该选的方向**。

### 单帧实际负载（不是估计）

| 内容 | 每帧 canvas 调用 |
|---|---|
| 背景地图 | **1 次 `drawImage`**（1280×1280 烤一次，按视口裁剪 blit） |
| 食物 | 视口内约 171 颗，按 6 色合批 → **6 次 fill + 6 次 stroke** |
| 球 | 单机 ~6~18 颗；联机最坏 8 人 × 8 分身 + 12 AI ≈ 76 颗，每颗 ~6 次操作 + 1 次 `fillText` |

典型帧几十次、最坏几百次，即每秒 7k~28k 次调用。这个量级下 canvas 2D 远远够用，
而且已经做过一轮有实测依据的优化（渐变按颜色缓存、食物合批、视口裁剪、空帧跳过重绘）。

**先量再谈**：`?debug=1` 的日志面板每秒打 `fps` 与 `frameMs`，测量工具已经现成。
任何"渲染慢"的怀疑都应该先拿真机数字验证，而不是先决定换什么。

### 换框架会实际失去什么

1. **零构建步骤是承重结构**。Pixi 压缩后 ~450KB、Phaser 1MB+：要么加打包器（破坏
   "浏览器直接加载源码"），要么走 CDN——后者直接**打死主部署路径**（手机同 Wi-Fi 扫码即玩，
   手机没有外网）。本地 vendor 还要改服务端静态白名单，而**单机玩家本来一个字节都不该付**。
2. **通用引擎自带主循环/物理**，而本项目最值钱的不变量是"服务端 import 的就是单机那份
   `core/World`、60Hz 固定步长、node 里能直接跑 127 条单测"（M0 抽 `Headless World` 的红利）。
   引擎的 loop 一进来，这个前提就开始漏水，而联机模式整个建立在它上面。
3. 手写渲染总共约 200 行，且是被完全理解过的代码。本仓库的历史恰好证明手写划得来：
   那次 perf 优化每一条都有实测数字；引入框架则是把问题换成"和框架搏斗"。

### 真正的天花板在视觉，不在性能

canvas 2D 做不到的是 metaball 黏连质感、叠加辉光/bloom、色彩分级、缩放畸变。
**如果动机是"球看起来太朴素"，那确实到顶了**——但正确解法是给**球这一层**写约 150 行裸
WebGL（一个 instanced 圆形 shader 就能做 metaball），UI 与食物继续留在 canvas 2D。
**不要**为解决一个 shader 的问题引入框架。

⚠️ **别用 `shadowBlur` 凑合**：canvas 2D 里最便宜的"假辉光"就是它，而它是著名的性能悬崖
（每次绘制强制走一次软件模糊），真机上会直接烧光帧预算。真要辉光就走 WebGL。

### 什么情况下才该重新评估

- 真机实测 `frameMs` 在中低端安卓上稳定超预算（先量，多半该优化文字/路径而不是换渲染）
- 目标明确变成胶质/metaball + 后处理 → 裸 WebGL 单层，不引框架
- 玩法扩到需要真正的粒子系统 / 多场景 / 补间动画管线（当前规模完全不需要）

迁移面（真要换时）：`Game.draw` / `Ball.draw` / `Map.draw` 三处 + 相机变换。
逻辑与渲染的分离在 M0 就做完了，所以不存在"重写游戏"这一说。

## AI 行为参数

决策优先级：逃离更大的球 > 追击更小的球 > 最近的食物 > 随机游走。决策每 `thinkInterval`(0.2s) 重选，转向每步算。

**`fleeRange`（normal 档当前 160）** —— 手感关键，两头都会坏：

| fleeRange | 平均存活 | 被吃轮次 | 被逼墙 |
|---|---|---|---|
| 120 | 29.4s | 12/20 | 高 |
| **160（normal 现值）** | **17.4s** | **17/20** | **3.6%** |
| 320 | 8.9s | 16/20 | 0% |

太大 → AI 一看见玩家就全程逃、永远抓不到；太小 → AI 懒得躲。

> 上表是**旧参数下的 20 轮数据**，只为记录"两头都会坏"这个形状。
> 更细的 120 轮扫描见下节「难度档位」：fleeRange 的最优区间在 130 附近，
> 而且 hard 档刻意取了**比 normal 更小**的 130（晚逃优于早逃）。

> 旧表里 160 行的"0.2%"是**错的**：那时的 `flee-sim.js` 没有调用 `resolveOverlaps`，
> 等于在一个没有软碰撞的世界里测的。补上之后猎手才真正贴得上猎物，贴墙率变成 3.6%。
> **仿真必须与 `Game.updateWorld` 同序（吃 → 弹开），漏掉任何一步都会得出假结论。**

**`escapeDirection` 的打分项**（`escapeSamples=16` 个均分方向，各探测 `escapeProbe` 距离）：

```
得分 = 离威胁更远(加) − 贴墙(减，越近减越狠) − 撞向别的球(减) − 靠近顺手食物(减)
```

没有这套打分时 AI 沿"远离威胁"直线跑，会被一路逼到墙角撞死（实测存活 2.9s → 11.5s）。
`escapePhase` 是每个 AI 独立的随机相位，重新决策时按 `escapeChange`(0.25) 换一侧，于是不同 AI 走位不同。

**`escapeFoodWeight`（当前 0.1）** —— 逃跑时顺手吃路边食物的吸引力：

| 权重 | 每轮多吃 | 被逼墙 |
|---|---|---|
| 0.25 | +1 颗 | **8.7%（破线）** |
| **0.1（现）** | 基准 | **1.3%** |

**AI 出生半径**：`[0.8, 2.2] × 初始半径`，上限 = 玩家当前半径 × `spawnRadiusRatio`(1.05)。
开局只放 `targetAiCount()` 个（= `minCount`），不按 `count` 放满，否则开局容易被围。
**AI 出生/重生优先挑相机视口之外的位置**（`rules.isOutsideView`），否则会在玩家眼前凭空出现、像"闪现"。

**AI 数量的"发展口径"（2026-10-11 真机反馈修的）**：`targetAiCount` / AI 出生体型的取样，
用的是 `World.developmentRadius()` = **整组质量开根**（等价半径），不能用「最大分身半径」。
分裂是质量守恒的，最大分身会瞬间减半——旧口径下一次分裂就让目标数量跨过下档边界
（r=55 时目标 9，分裂后最大分身 38.9 → 目标 7），超编机制当场**永久移除最大的 AI**：
玩家在追的人机追着追着就消失了。无头复现 9→8，修复后 9→9（质量守恒 → 口径不动）。
整组质量死亡归零，死后 AI 按新出生体型重新平衡，语义正好。

**AI 互相避让（`avoidGap` / `avoidWeight`）**：小球靠近到「双方半径 + 55」以内会按接近程度互相推开，
所有模式都生效（觅食/追击/游走/逃跑）。之前只有逃跑的 `escapeDirection` 算了"别撞球"，
觅食和追击完全不避让，再叠加"所有 AI 都选最近的同一颗食物"，于是它们走成一条直线。
**逃跑时要跳过当前威胁**——`escapeDirection` 已经算过一次，重复叠加会让猎物过分灵活
（实测玩家平均存活 17.4s → 30.0s、贴墙 0.2% → 5.9%），跳过之后回到 17.4s / 0.2%。

避让效果（90 秒拥挤度仿真，邻居 = 身边 80 单位内的 AI）：

| AI 数量 | 两两平均距离（改前→改后） | 平均邻居数（改前→改后） |
|---|---|---|
| 6 | 346 → 271 | 0.24 → 0.34 |
| 8 | 270 → **336** | 0.91 → **0.26** |
| 12 | 298 → **343** | 0.96 → **0.43** |

（6 AI 那档反而略挤，是因为地图大、球只有 6 个，差异在噪声范围内。）

**目标认领**：`think()` 会跳过其他 AI 已经盯上的猎物/食物（看它们的 `targetBall`/`targetFood`/`escapeFood`），
否则一群 AI 会同时奔向同一个点。

## 难度档位（easy / normal / hard）

体检脚本：`node scripts/difficulty-report.mjs`（**会自己判定验收线，不合格 exit 1**）。

### 先修度量，再调参

这个档位曾经"配了参数但量不出来"，根因是**两个度量盲区**，不是参数没调：

| 盲区 | 症状 | 修法 |
|---|---|---|
| 报告只数「吃了几颗食物」 | `foodGain` 改的是**每颗的肉**，颗数一样而肉量差三成，梯度在报告里是平的 | food-sim 增加「AI 30s 平均体重」列 |
| 猎手永远是瞄当前位置的直线球 | `chaseLead` / `chaseRange` 是 AI 压宝的机制，仿真里量不到 = **死参数** | flee-sim 增加 `--hunterLead N`，与 `AI.chaseLead` 同一套机制 |

修完之后同一组参数（旧的 easy/normal/hard）实测：

| | AI 30s 体重 | 被吃(直线) | 被吃(预判) |
|---|---|---|---|
| 旧 easy | 1051 kg | 18/20 | 20/20 |
| 旧 normal | 1579 kg | 17/20 | 19/20 |
| 旧 hard | 1922 kg | 17/20 | **20/20** |

体重梯度**一直是真实的**（档差 83%），只是看不见；而被吃率梯度是平的，且**旧 hard 在预判猎手下比 normal 更好抓**。

### 三个反直觉结论

1. **`escapeSamples` 在 16 以上饱和**。24 / 32 与 16 实测无差别（40 轮：29~32 / 36~37），
   它只在 16 以下才是有效杠杆（8 → 被吃 +8/+3）。**不是**难度杠杆。
2. **`escapeChange`（乱改主意的概率）不能当难度杠杆**。对两种猎手都没有单调效应；
   旧 hard 把它压到 0.12（"更聪明"），结果 AI 行为更可预测、**更容易被抓**。hard 因此沿用 normal 的 0.25。
3. **`fleeRange` 非单调，130 附近是最优**——不是"越大越聪明"。晚逃 = 等威胁真的逼近再决定、
   一次逃对方向；早逃 = 一路狂奔撞墙角。hard 的 fleeRange(130) **小于** normal(160) 就是这个道理。

另外：`thinkInterval` 调快单看会让 AI 更多被吃（决策更快 = 行为更可预测）。

**参数效果不可加**：`thinkInterval=0.06` 单独扫是 +6/40（更差），合进 hard-2 却是全场最好的一档。
所以任何一档都必须整档跑 `difficulty-report.mjs` 验，不能靠单参数扫描外推。

### 当前三档（difficulty-report 实测，flee 侧 60 轮）

| 档位 | fleeRange | thinkInterval | escapeSamples | escapeProbe | escapeChange | **fleeOrbit** | 被吃(直线) | 被吃(预判) | AI 30s 体重 | 被逼墙 |
|---|---|---|---|---|---|---|---|---|---|---|
| easy | 190 | 0.15 | 8 | 150 | 0.5 | **0** | 58/60 (97%) | 60/60 (100%) | 1263 kg | 0.6% |
| normal | 160 | 0.1 | 16 | 180 | 0.25 | **0.4** | 48/60 (80%) | 54/60 (90%) | 1579 kg | 0.5% |
| hard | 130 | 0.06 | 24 | 270 | 0.25 | **0.65** | 41/60 (68%) | 50/60 (83%) | 1922 kg | 1.9% |

**验收线**（脚本自动判）：两种猎手口径下被吃率 easy > normal > hard 单调；
AI 30s 体重三档单调且档差 ≥15%；normal 的 AI/玩家食物比守住 0.867 锚点；
normal 必须与不带 flag 的基线逐位一致。

**normal 必须是 `AI.*` 默认值的逐项拷贝**。它既是默认档又是历史锚点，
`difficulty-report` 会拿"不带 flag 的 flee-sim"当参照逐位比对，漂了就报出来。
⚠ `difficulty-report` 的参数表里**必须逐档传 `fleeOrbit`**：不传的话三档都跑 AI 默认值，
报告就会在"参数配了"的前提下量出一个假梯度——这正是本节开头那两个度量盲区的同款错误。

flee 侧用 60 轮而不是默认的 20：hard 与 normal 在预判口径下的真实差只有 10 个点，
20 轮的抽样噪声就有 ±7 个点——验收线要是抖的，它等于没有，还会让人反复重跑"求个通过"。

### 绕圈拖延（`AI.fleeOrbit*`，2026-10-17 实测）

**机制**：逃跑方向不再只由「离威胁更远」这一项决定，还在打分里给**切向**
（垂直于逃离连线）加一个偏置，于是 AI 会挑斜着跑的那个候选。
直退是唯一能被预判出来的走位——猎手瞄「位置 + 速度×提前量」时，径向直退正好把
提前量用满，于是贴上来的球几乎必被吃到。

**120 轮扫描**（`flee-sim --trials=120 --hunterLead=0.25`，被吃/120）：

| fleeOrbit | 被吃(直线) | 被吃(预判) | 平均存活(直线) | 平均存活(预判) | 被逼墙(直线) | 被逼墙(预判) |
|---|---|---|---|---|---|---|
| 0（现状） | 91 | 105 | 29.5s | 23.4s | 2.5% | 1.8% |
| **0.4（当前）** | **84** | **100** | **35.2s** | **29.3s** | 2.7% | 0.3% |
| 0.8 | 93 | 106 | 35.1s | 29.8s | 1.8% | 0.9% |

0.4 是拐点：存活时间 +19%/+25%，被吃率降 7/5 个点，贴墙率不涨。0.8 起边际收益消失
（存活时间不再涨、被吃率反而回到基线），因为偏置压过了「离威胁更远」那一项，
AI 开始横向浪费速度。

**三个参数耦合**：`fleeOrbit`(强度) × `fleeOrbitReach`(70 世界单位) 决定偏置大小，
与候选方向之间的弦长 `2 × escapeProbe × sin(π/escapeSamples)`（16 样本时约 70）同量级；
`fleeOrbitNear`(60) 是闸门下界。

**踩过的两个坑**（别退回去）：
1. **闸门必须落在 `fleeRange` 之内**。第一版把上界设在 `fleeOrbitRange=240`，
   而 `fleeRange` 只有 160——AI 根本不会逃到那么远，闸门永远打不满，
   `fleeOrbit` 成了死参数，40 轮实测全落在噪声里（29/29/29/30/30 vs 基线）。
   这类"配了但量不出来"的现象本项目吃过两次（chaseLead、count），第一次一定会踩。
2. **必须做打分偏置，不能旋转选出来的方向**。旋转发生在贴墙/撞球惩罚项算完之后，
   转完可能正对着墙：旋转版实测强度 ≥0.65 时被逼墙从 0.9% 飙到 4~5%，
   而"被逼墙角"正是 AI 被抓的主要原因之一。偏置让打分函数自己去挑，
   墙的约束一直在，绕不出去就不绕。

**没做的**：引诱玩家靠近别的球（需要"AI 与玩家互相影响"的度量，两个仿真都只有单球，
量不出来，硬做等于凭感觉改难度曲线）。

### 这套度量**没有**覆盖的

`DIFFICULTY.*.count`（5/9、6/12、7/14）的梯度没有自动化度量——food-sim 与 flee-sim 都只跑单个球。
改它只能靠真机体感。hard 的 `chaseRange`/`chaseLead`（AI 主动压宝）同理，
它在 flee-sim 里是死参数（本 sim 的猎物只逃不追）。

## AI 之间会不会互吃

会，但**稀疏**。无头仿真（90 秒、只有 AI、无食物补给差异）实测：

| AI.eatBonus | 6 AI | 8 AI | 12 AI |
|---|---|---|---|
| 1（原始） | 6 次，体型 20.6~48.5 | 11 次，16.2~38.1 | 22 次，9.8~42.2 |
| **1.3（当前）** | 10 次，11.5~60.3 | 10 次，9.7~59.5 | 22 次，8.2~68.4 |
| 1.6 | 15 次，8.6~111.8（滚雪球） | 13 次，9.3~63.6 | 18 次，10.4~58.0 |

为什么玩家几乎看不到：一次互吃只给 `0.85 × 对方质量`（r=10 的猎物 ≈ 85 质量，对 400 质量的捕食者是 +21% 质量、**半径只涨 4%**），
而且大多发生在屏幕外。`eatBonus` 就是为了把这个"看不见的成长"放大到能被察觉，1.6 会滚雪球出霸主，故取 1.3。
注意倍率越高 AI 整体越肥（12 AI 合计质量 6350 → 9766），游戏会变难——再往上加之前先重测难度。

复现：改 `AI.eatBonus` 后跑 AI 互吃仿真（见下方脚本骨架，同样要固定种子）；只看 `npm run sim` 不够，
那个脚本里的猎物只吃食物、不吃别的球，测不到 eatBonus。

## 「大球追不上」的验收口径

**别看速度公式下结论**：

- 真正的小体型硬门槛是**互吃比例**（`r > 对方r × 1.15`）。猎手 r=10 对 r=10 是 **0/20** 轮吃到，r=12 就 **20/20**——差一点点永远吃不到，跟速度无关。
- 速度只是一阶估算。实测猎手比猎物慢 40%（r=50 vs r=10）仍抓到 **16/20**，因为逃命 AI 达不到理论速度、有界地图躲不了角落、还会边逃边长大。

```bash
npm run sim -- --sweep              # 扫猎手半径 10~50，出"理论直退 vs 实测被吃"对照
npm run sim -- --hunter 30 --prey 15
npm run sim -- --nofood             # 关掉"猎物边逃边长大"，把速度因素单独隔离出来
```

## 联机仿真（延迟下的实测）

`npm run sim:net` —— 联机版的 flee-sim。真 socket.io + TCP 代理注入延迟，
三客户端（吃球方 / 被吃方 / 旁观端）跑真实对局，客户端跑的是真实的 `src/net/client.js`。

在此之前，联机的预测/对账只在 **LAN 直连（≈0ms）** 的浏览器里手测过一次（误差 4 单位）。
0 毫秒下所有网络问题都不存在，"150ms 下预测会不会飘"一直没有证据。

| 单向延迟 | 预测平均误差 | 阈值（视口宽 2%） | 输入突变后收敛 | 每端下行 | 快照频率 |
|---|---|---|---|---|---|
| 80ms（RTT 160ms） | 5.1 世界单位 | 20.5 | 4ms | 0.7 KB/s | 16.1 Hz |
| 150ms（RTT 300ms） | 4.5 世界单位 | 19.5 | 22ms | 0.7 KB/s | 15.9 Hz |

互吃一致性（四处对同一个数）：被吃方收到 `eaten`（凶手正确）→ 自己的视图知道死了 →
旁观端视图里那颗球消失且吃球方质量与本人**逐位相同** → 吃球方质量按 `EAT.absorb` 增长。

⚠ 吃球方那条**只卡下限**（实测 +85 ~ +267 都算过）：摆完位它站在原地，
路过的 AI 会自己撞上来被一起吃，它自己也一直在吃食物（r=40 站几秒 ≈ +200kg），
"增量必须正好等于 preyMass × absorb"在这条路径上不可测。精确算式由 `npm test` 的
`absorb` 用例守着，"两端对同一个数"由上面那条旁观端一致性守着。

**验收线**（脚本自动判、不合格 exit 1）：平均误差 < 视口宽 2%、输入突变后 500ms 内收敛、
互吃四处一致、每端下行 < 10KB/s、快照 ≥15Hz、断线重连四条。

### 断线重连（M4，2026-10-17 实测）

仿真里把宽限期用 `SUPERPOP_GRACE_MS=1200` 压到 1.2s（真机值是 `NET.graceSeconds=10`），
阶段 4 用旁观端当主角：断线 → 别的端仍看得见那颗球 → 带令牌重连 → ownerId 与 cid 都不变、
还有活细胞 → 断了不回来 → 宽限期满被移除并广播 `left`。80ms 档四条全绿。

三个数值/顺序上的约束（都是实测踩出来的）：

- **认领判断要在「房间已满」之前**：宽限期内的组本来就占着 `MAX_PLAYERS` 的名额
  （它还在场上），反过来判会把自家重连挡在门外。
- **断线期间不发 `left`**：人还在场上，只是操控权没了。花名册要重发一次，
  让对端刷新（兼带把 AI 超编移除等变化带过去）。
- **宽限期内被 AI 吃光**要靠 `welcome.death{mass,rank}` 带回死亡瞬间的数据：
  `eaten` 事件那时没有 socket 可发，而此刻 cells 全是 `alive=false`，
  客户端自己算出来是 0kg、名次也排不出来。

### 让仿真确定化的两件关键事

1. **给所有端挂护盾**：`resolveEatings` 只在**受害者**侧查 `isProtected`，
   所以挂着护盾的球死不了、却照样吃得掉人。不这么做，阶段 1 里满舵乱跑的球有概率被 AI 吃掉，
   摆位钩子变成 no-op，仿真随机失败（实测 4 轮里有 1 轮挂）。
2. **`debug:place{x,y,r,shield,unshield}`**（`SUPERPOP_DEBUG=1` 才注册，与 `debug:forceCrown` 同级）：
   靠 AI 漫游撞出一次互吃是概率事件，跑十次不一定碰上一次——那样的断言等于没有断言。

## 仿真脚本用法

两个脚本都：**固定随机种子**（结果可复现）、**支持参数覆盖**、**只输出少量关键指标 + 异常提示**。

```bash
npm run sim                                   # AI 逃跑：fleeRange/escapeProbe/escapeWallWeight/escapeFoodWeight/escapeFoodRange
npm run sim -- 160 180                       # 位置参数按上面顺序覆盖
npm run sim -- --sweep --hunter 30 --prey 15 --nofood
npm run sim -- --trials=40                   # 加大轮次：20 轮的 ±6.6% 噪声会翻转结论（本次提速定案用的 80 轮）
npm run sim:food                              # 食物密度/速度剖面/成长对比
npm run sim:food -- --divisor 44 --slowdown 0.8 --playerGain 0.6 --foodGain 0.25
npm run sim:net                               # 联机：注入 80/150ms 延迟，验预测/互吃/带宽
npm run sim:net -- --latency 200 --seconds 20  # 只跑一档并加长观测时长
```

- **调速度/AI 参数时 flee-sim 用 `--trials=40` 以上**：20 轮下"44/0.8 被吃 72.5%"看着
  像回归，80 轮复核是 76.3%（基线 77.5%）——差值全在噪声里。
- **批量传参用 `--名字=值` 的粘连写法**：分开写时两个 flag 恰好同值（如
  `--thinkInterval 0.1 --escapeFoodWeight 0.1`）会触发 args.js 的撞值护栏整组报错。

**写仿真脚本时的坑**（都踩过）：

- 密度公式用**面密度 `λ`**（单位²），不是平均间距（单位长度）——用错会让所有结论偏一个数量级。
- 参数解析要区分 flag 的值和位置参数：`--divisor 60` 里的 `60` 若又被当位置参数，会顺手改掉别的配置，
  导致整组对照数据作废（当时就是这么废掉一轮的）。**验证方式：不带参数跑一遍，结果应与不带覆盖的 `npm run sim` 一致。**
- 解析模型和仿真矛盾时，先怀疑仿真里的硬编码假设（例如猎手半径写死 22，正好没覆盖失败的体型区间），
  并把结论降级为"倾向 + 需补测"，不要拿手算冒充仿真结果。
